2. 문제 정의

2.1 우리가 겪은 문제

주말마다 "어디 갈까"만 이야기하다 결국 아무 데도 못 가는 일이 반복됐습니다. 가고 싶은 마음이 없어서가 아니라, 어디를 갈지 정하고 코스를 짜는 과정에서 지쳤기 때문입니다.

2.2 우리만의 문제가 아니었다

주변 50명에게 직접 물었습니다. 답은 거의 같았습니다.

2.3 기존 해법의 한계

기존 여행 앱들은 이 문제를 더 많은 정보와 더 많은 선택지로 풀어 왔습니다. 추천 리스트가 길어지고 필터가 정교해질수록 사용자가 비교해야 할 대상도 함께 늘어납니다.

하지만 사람들이 실제로 멈춰 서는 지점은 정보 부족이 아니라 결정 그 자체였습니다. 선택지가 늘수록 포기도 함께 늘었습니다. 방향이 반대였던 것입니다.

2.4 왜 우리가 해결하고 싶은가

이것은 저희가 직접 겪은 문제입니다. 그래서 남을 위한 서비스가 아니라 저희가 쓰고 싶은 방식으로 만들 수 있었습니다. 기획 회의에서 "이 기능이 있으면 우리가 쓸까?"를 판단 기준으로 삼았고, 그 질문을 통과하지 못한 기능은 넣지 않았습니다.

4. 솔루션

4.1 접근 방식

선택지를 늘리는 대신 결정을 대신 가져옵니다. 사용자가 하는 일은 두 가지뿐입니다 — 예산을 정하고, 취향 질문에 답하는 것. 나머지 결정은 AI가 합니다.

여기에 하나를 더했습니다. 장소를 도착 전까지 알려주지 않는 것입니다. 미리 알면 다시 검색하고 비교하게 되어 결국 같은 피로가 반복되기 때문입니다. 비공개는 연출이 아니라, 결정 피로를 없애기 위한 설계입니다.

4.2 사용자 흐름

  1. 지역 · 예산 · 기간 선택 — 수도권 안에서 고르고, 예산은 슬라이더로 조정합니다
  2. 취향 질문 8개 — 한 화면에 하나씩. 여행 목적, 성별, 연령대, 좋아하는 음식, 많이 걷는 걸 좋아하는지까지 묻습니다
  3. 자연어 취향 입력 — "조용한 카페 위주로" 같은 문장을 그대로 받아 장소 선택에 반영합니다
  4. AI 플랜 설계 — 예산 배분과 추천 이유는 보여주되, 장소 이름은 가립니다
  5. 여정 안내 — 발밑의 길이 조금씩만 열립니다. 전체 경로는 보이지 않습니다
  6. 도착 공개 — 도착한 그 순간에야 이름 · 주소 · 평점이 나타납니다

4.3 핵심 기능

기능설명
취향 기반 AI 일정 설계 프로필과 자연어 메모를 로컬 LLM에 넘겨 장소를 고르고, 왜 그 장소인지 이유 문장까지 생성합니다
목적지 비공개 안내 도착 전까지 장소를 숨기고, 다음 구간의 경로만 조금씩 공개합니다
예산 자동 배분 숙박 40 · 관광 30 · 식비 20 · 교통 10 비율로 나누고, 초과분은 항목 간 자동 조정합니다
취향 필터 "많이 걷기 싫다"고 답하면 산 · 트레킹 코스가 후보에서 제외됩니다
동선 최적화 최근접 이웃 휴리스틱으로 이동 시간을 최소화하고 대중교통 경로를 붙입니다
시뮬레이션 모드 GPS 없이도 여정을 1× / 3× / 10× 배속으로 돌려 도착 공개까지 체험할 수 있습니다

5. 시스템 구성

5.1 아키텍처

사용자 요청은 백엔드의 플랜 서비스로 들어갑니다. 플랜 서비스는 프로필을 로컬 LLM에 넘겨 장소 후보와 추천 이유를 받고, 받은 결과를 예산 · 동선 제약에 맞춰 다듬어 최종 일정을 만듭니다. LLM 호출이 실패하거나 지연되면 자체 휴리스틱 알고리즘이 같은 자리를 대신합니다.

계층구성
클라이언트Android 앱 (Jetpack Compose) · 웹 (Vanilla JS + Leaflet)
API 서버Kotlin + Spring Boot 3.5 · JPA · H2
AI 계층로컬 LLM (LM Studio · OpenAI 호환 API) + 휴리스틱 폴백
외부 연동TMAP POI · 국토부 TAGO · ODsay · OSRM · CARTO 지도 타일
배포자체 서버 · VPN 터널링 · systemd 상시 구동

5.3 AI 활용 방식

프로덕트에 들어간 AI — 사용자 프로필(연령 · MBTI · 여행 목적 · 음식 취향 · 보행 선호 · 자연어 취향 메모)을 프롬프트로 구성해 로컬 LLM에 전달하고, 장소 선정 · 일정 구성 · 추천 이유를 생성합니다.

폴백 설계 — LLM은 언제든 느려지거나 멈출 수 있습니다. 그래서 평점 · 근접도 · 예산 제약 스코어링과 최근접 이웃 동선 최적화로 구성한 자체 알고리즘을 같은 인터페이스로 만들어 두었습니다. AI가 멈춰도 서비스는 멈추지 않습니다. 외부 API 키가 하나도 없어도 수도권 시드 데이터로 전체 흐름이 동작합니다.

개발 과정의 AI — Claude (Anthropic)를 설계 · 구현 · 리뷰 전 과정에 활용했으며, 사용 내역을 저장소 README에 전면 공개했습니다. 기획 · 아이디어 · 검증은 팀이 수행했습니다.

  • 계획 수립에 드는 평균 14시간을 수 분으로 단축
  • 결정 피로 없이 실행되는 여행 — "가고 싶었지만 못 간" 수요를 실제 방문으로 전환

  • AI가 고른 지역 상권으로 방문객을 자동 송객, 소상공인 유입 경로가 됩니다
  • 축적된 여행 패턴 데이터는 지자체 · 관광공사의 정책 자료로 활용 가능합니다

8. 개발 현황

8.1 완료

  • Kotlin Spring Boot 백엔드 — 플랜 생성 API, 예산 배분, 동선 최적화, 취향 필터
  • 로컬 LLM 연동 및 휴리스틱 폴백 이중화
  • Android 앱 (Compose) — 설정 · 8문항 온보딩 · 플랜 · 여정 · 도착 공개 전 화면
  • 웹 서비스 — 앱과 동일한 UI, 지도 · 시뮬레이션 모드 포함
  • 자체 서버 배포 — VPN 터널링 구성, systemd 상시 구동, 외부 접속 검증 완료

8.2 현재 한계 (정직하게)

  • 예약은 토큰 선결제 시뮬레이션입니다. 실제 PG · 제휴 연동은 다음 단계입니다
  • 가격 · 평점 일부는 추정치입니다. TMAP POI가 가격 정보를 제공하지 않기 때문입니다
  • 서비스 지역이 수도권으로 한정됩니다. 범위를 좁혀 완성도를 택한 결과입니다
  • 현재 프로덕트 URL은 HTTPS가 아니어서 브라우저 GPS 권한을 쓸 수 없습니다. 대신 시뮬레이션 모드로 전체 경험을 체험할 수 있습니다
